# 智能旅行规划系统（Smart Travel）

> 基于 RAG 的城市旅行行程规划系统。用户选好城市、兴趣、同行人、天数和住宿区，
> 系统从景点知识库检索候选，按地理分天、按风格选点，最后由大模型写成每天一条顺路的行程。

## 它解决什么问题

一次自由行的规划，本质是在解三个问题：

1. **选什么点**——用户说「我想看历史、吃小吃」，系统得知道武汉有哪些相关的地方；
2. **怎么分天、怎么排**——几天行程不能天天横跨全城，得大致顺路；
3. **怎么写成人话**——给出「先去哪、再去哪、几点去、为什么这么排」。

常见做法是「把一堆景点丢给大模型，让它自由发挥」。这条路的通病是：

- 大模型没有坐标，排出来的行程**地理上不可控**（今天在城东、下午在城西）；
- 大模型会**编造不存在的景点**，或者把已过滤的脏数据写进行程；
- 三套「风格方案」往往只是换了措辞，**内容上没区别**。

本项目的核心思路是 **「算法定内容，大模型定文案」**：

```
检索召回 → 地理分天 → 按风格选点（点定死）→ 大模型只负责把这一天写成一段话
```

选点和分天由确定性算法完成，大模型不参与「去哪」的决策，只负责叙述。
这样行程天然顺路、不编造、可控、可复现。

## 效果一览

- 知识库规模：**武汉 137 条 POI**（由 238 条打标数据归组、去噪、合并而来）
- 行程输出：**按天分段**的完整文案，每天 4~5 个景点，附地图与景点图片
- 三种风格：**综合 / 口碑 / 悠闲**，用户在表单里先选，只生成那一种
- 检索评估：Hit Rate@40 = **0.660**，MRR = **0.276**，Noise Rate = **0.000**
  （10 条前端场景用例，见 [评估](#5-eval-评估)）

## 数据流水线

五步流水线，每步独立、可单步重跑，中间产物都落盘，便于排查。

```
crawl ──▶ clean ──▶ tag ──▶ build ──▶ eval
抓取      清洗      打标     建库      评估
raw/      processed/  processed/  knowledge_base/  eval/reports/
```

武汉各阶段的数据量（便于理解每一步「筛掉多少」）：

| 阶段 | 产物 | 条数 |
|---|---|---|
| crawl | `data/raw/wuhan_pois.json` | 抓取原始 POI |
| clean | `data/processed/wuhan_clean.json` | 246 |
| tag | `data/processed/wuhan_tagged.json` | 238 |
| build | `data/knowledge_base/wuhan_v1.jsonl` | **137** |

### 1. crawl 抓取

两个来源合并：

- **核心词**：`config/cities/{city}.yaml` 的 `core_spots`（按兴趣分组，如「历史人文: 黄鹤楼、晴川阁…」）。每个词单独搜，命中打上 `_interest_group` 标记。
- **类别词**：`category_words`（美食街、风景区、寺庙…），补充长尾。

同时抓**锚点**（交通枢纽、住宿区）的坐标，供空间排序当起点用。
带指数退避重试、断点续跑（产物已存在则跳过，`--force` 重抓）。

### 2. clean 清洗（两层过滤）

景点数据里混着停车场、地铁站、学校、品牌店、景点内部的子设施。清洗用**优先级队列**逐条判定（规则全在 YAML，代码零硬编码）：

| 优先级 | 规则 | 结果 |
|---|---|---|
| 0 | `hard_exclude_*`（停车场 / 售票处 / 地铁站…） | **剔除，不可豁免** |
| 1 | 名字**完全匹配** `core_spots` | 保留 |
| 2 | 带 `_interest_group`（核心词抓来的） | 保留 |
| 3 | `soft_exclude_*`（学校 / 政府机关…），名字含豁免词则保留 | 留 / 剔 |
| 4 | 品牌店正则（`黄鹤楼(香港路特许店)`） | 剔除 |
| 5 | 子设施后缀（`归元禅寺-大雄宝殿`） | 剔除 |
| 6 | 城市特有黑名单（`local_exclude`） | 剔除 |
| 7 | 通过 | 保留 |

硬过滤排在所有豁免之前：「司门口黄鹤楼（地铁站）」不会因为名字含核心词「黄鹤楼」而被放进来。

### 3. tag 打标签

每条 POI 调一次 `qwen3.5-flash`，一次输出四个字段（一次调用，省成本、保证一致）：

| 字段 | 含义 | 来源 |
|---|---|---|
| `is_attraction` | 是不是「值得专程去的旅游目的地」 | LLM 判定 |
| `tags` | 兴趣标签（1~3 个） | 从固定词表选 |
| `behaviors` | 体验词（2~5 个） | 从固定词表选 |
| `description` | 一句话描述（只写特点，不写「适合谁」） | LLM 生成 |

固定词表（`config/schema.yaml`）：

- `interest_tags`：历史人文 / 自然风光 / 美食探店 / 购物休闲 / 夜生活
- `behavior_tags`：散步 / 拍照 / 看展 / 赏景 / 逛街 / 美食 / 研学 / 遛娃 / 热闹 / 安静 / 文艺 / 夜游

支持断点续跑（已处理的 id 跳过）、单条失败不中断、每条处理完立即落盘。

### 4. build 建库（同名归组 + 向量化）

这一步把「POI 记录」变成「可检索的知识库」，做了两件关键的事。

#### 4.1 同名归组：一个主景点 = 一条记录

高德会把同一个景点的多个切面返回成多条 POI，例如：

```
户部巷       户部巷风情街       户部巷小吃一条街       户部巷美食第一巷
江汉路步行街   江汉路嗨吃街       江汉路·前进五路小吃美食一条街
黄鹤楼       黄鹤楼公园         黄鹤楼故址
```

如果原样入库，检索时它们会互相挤占名额，同一趟行程里还可能出现两个「户部巷」。
因此在 build 阶段**合并成一个「主景点」**：

- **canonical（组名）** = 全库里「能作为该名字子串的最短名字」。
  - `户部巷风情街` / `户部巷小吃一条街` 都包含 `户部巷` → 归到 `户部巷`；
  - 没有更短名字可包含的（如 `东湖听涛景区` / `东湖磨山景区`）各自独立。
- **人工兜底**：`config/cities/{city}.yaml` 的 `poi_groups` 可以显式合并 / 拆分自动规则覆盖不到的组：
  ```yaml
  poi_groups:
    江汉路: [江汉路步行街, 江汉路嗨吃街, 江汉路·前进五路小吃美食一条街]
    江汉关: [江汉关博物馆, 江汉关大楼]
    no_merge: [杨正古铁佛寺]      # 显式拆分，不参与自动归组
  ```
- **合并规则**：
  - `name` = canonical；`aliases` = 其它成员名（去重保序）
  - `rating` = 组内最大
  - `tags` / `behaviors` = 组内**并集**（如「晴川阁」组并进「看展 / 研学」）
  - 坐标、地址等其余字段取代表记录（rating 最高）

这样每个主景点在库里只有一条，**同一趟行程天然不会重复**。
变体名进 `aliases`，既进 embedding 文本（让「户部巷风情街」这种查询也能命中该组），
也交给大模型（生成时可以自然带一句「顺路逛逛风情街」）。

顺带清洗两个派生字段：

- `level`：从脏的 `poi_level` 里正则抽 `5A/4A/3A`（`poi_level` 字段混了类型词，如「特色商业街」，不可直接用）
- `display_name`：去掉括号后缀，如 `古德寺(宗教活动场所)(暂停开放)` → `古德寺`

#### 4.2 向量化 + 建索引

按 `schema.yaml` 的 `text_template` 把字段拼成一段自然语言，再交给 embedding：

```
{name}{aliases}，位于{city}{district}。类型：{clean_type}，属于{tags}类，可以{behaviors}。
{description}
```

产出三份等价的数据：

- `chroma_db/{city}_v1/`：向量库（每条一个 embedding）
- `data/knowledge_base/{city}_v1.jsonl`：易读的存档
- `data/knowledge_base/{city}_bm25.pkl` + `_meta.pkl`：BM25 索引

### 5. eval 评估

评估集按**前端表单场景**组织（`data/eval/{city}_eval.json`）：每条用例 = 一次典型的表单填写
（风格 / 兴趣 / 同行人 / 天数 / 住宿区）。**query 不手写**，而是由 `interests` 直接拼成
（如「历史人文 美食探店」）——和生成流程实际发出的 query 完全一致。

| 指标 | 定义 | 公式 |
|---|---|---|
| **Hit Rate@K** | 期望结果有多少进了 top-K | `命中数 / 期望数` |
| **MRR** | 第一个命中结果的排名倒数 | `1 / rank_first_hit` |
| **Noise Rate@K** | 不该出现的混进 top-K 的比例 | `混入数 / must_not 数` |

匹配用**包含匹配**（`黄鹤楼` 被 `黄鹤楼公园` 命中即算命中），因为高德返回的名字常带后缀，
用精确匹配会让评估集全部判错。

武汉当前结果（10 条前端场景用例）：

| top-K | Hit Rate | MRR | Noise Rate |
|---|---|---|---|
| @40（对齐产品候选池） | **0.660** | 0.276 | 0.000 |
| @60 | 0.880 | 0.277 | 0.000 |
| @10 | 0.230 | 0.250 | 0.000 |

> K 取产品实际的召回量级（召回 = `max(40, 天数 × 20)`）。
> Noise Rate 为 0，说明清洗到位——非景点（停车场 / 地铁站 / 售票处）没有混进候选池。
> Hit Rate 反映的是「按所选兴趣召回候选池」的覆盖度。

**关于「标准答案」**：评估集里写的「期望景点」只是**代表性答案，不是唯一解**。
旅游本来就没有标准答案——`楚河汉街` 算购物休闲，`昙华林` 既算历史人文、也算拍照打卡；
同一句兴趣，不同的人心里的名单可以差很远。

因此本项目的检索定位是**倾向性召回**：把「大概是这些地方」捞进候选池，而不是做精确判定。
捞进来之后，去不去、怎么排，交给后面的分天与选点。
所以评估指标衡量的是这个「倾向」的覆盖度，**不必追求满分的 Hit Rate**——
把该来的都捞进池子（Hit Rate 高）比「只捞对的」（Noise 低但漏）更符合产品目标。

**关于「多样化」**：embedding 文本里除了 `tags`，还刻意放了 `behaviors`（能做什么）和 `description`（一句话描述）。
这不是冗余——**旅行偏好不是互斥的**：倾向于历史人文的人，一样想去小吃街吃顿地道美食、去步行街逛逛。
所以候选池本来就应该是「兴趣为主 + 适度相关」的混合体，而不是严格筛选后的集合。

这也就解释了为什么 Hit Rate 不需要很高：池子里多出来的那些「相关但不同类」的项，是**有意保留的多样性**，
而不是噪声。评估指标在这里的作用是**体检**——看趋势、防退化，而不是追求满分。
真正的取舍发生在后面的分天与选点：**池子宽一点，选点时才有得挑。**

## 检索层：向量 + BM25 + 加权 RRF

一条 query 同时走两路，再用 **加权 Reciprocal Rank Fusion** 融合。

**两路召回**（多召回，给融合留空间）：

- 向量检索：Chroma，`top_k × 5`
- BM25：`jieba` 分词后检索，`top_k × 2`，**只保留分数 > 0 的文档**

**加权 RRF**：

```
score(d) = w_vec / (k + rank_vec(d)) + w_bm25 / (k + rank_bm25(d))

k      = 60      # 平滑参数（标准值）
w_vec  = 1.0     # 语义为主
w_bm25 = 0.3     # 关键词为辅
```

> 向量输出的是 L2 距离、BM25 输出的是词频分数，**两者量纲不可比**，没法直接相加。
> RRF 只用「排名」，天然可融合。

**两个细节**：

- `city` 是唯一的硬过滤（防止跨城市串结果），在 Chroma 用 `filter` 实现。
- query 里的城市名会被剥掉：所有 POI 文本都含城市名，不剥的话 BM25 会被城市名刷分。

## 规划层：分天 + 选点

这是整套系统的核心，分两步：**先把候选按地理分成 N 天，再在每天里挑几个点**。

### 空间分天 spatial_sorter

抽象：**「簇」是地理单位，「片」才是「天」；一天 = 1~N 个簇。**

```
1. 过滤无效坐标
2. 切小簇    KMeans 聚 k 簇 → 每簇超 max_size 递归拆 → 簇内最远两点超 max_dist 再拆
3. 单点吸收   城区单点簇吸进离它最近的城区多簇
4. 城郊分离   按区名表判定：城区簇参与分天，郊区簇搁置
5. 聚片      对簇心 KMeans 聚成 days 片
6. 纠错      每簇归到最近的片，先算归属再统一更新，循环到稳定
7. 补簇      片点数 < min_pts_per_day 的，从就近且搬得起的片挪簇
8. 片排序    Day1 = 离住宿区最近的片，之后贪心找最近的下一片
```

关键参数（`config/cities/{city}.yaml` 的 `spatial`）：

| 参数 | 武汉取值 | 含义 |
|---|---|---|
| `cluster_k` | 12 | KMeans 初始簇数上限 |
| `cluster_max_size` | 5 | 每簇最多几个点，超过递归拆 |
| `cluster_max_dist` | 8.0 km | 簇内两两最大距离，超过拆 |
| `min_pts_per_day` | 6 | 每片最少几个点 |
| `urban_districts` | 7 个主城区 | 城郊分离依据 |

城/郊用**区名表**判定，而不是「离住宿区距离」：距离阈值要调，设宽了把远郊算近郊、
设窄了又把城区算远郊；主城区是地理事实，写死更准，换城市补一份即可。

跨江不特殊处理——武汉地铁过江方便，跨江点和普通点一样参与分片。

### 片内选点 poi_picker

从某一天的候选里挑 N 个点。每个候选算一个**基础分**，抽点时再乘一个**距离惩罚**，最后**加权随机抽取**。

**基础分（六项加权和）**：

```
base(p) = w_rating · r̂(p)          # 评分，r̂ = rating/5；无评分按 0.6
        + w_interest · I(p)        # 兴趣匹配 = 命中标签数 / 所选兴趣数
        + w_random · U             # 随机项，U ~ Uniform(0,1)
        + w_core · C(p)            # 是否核心景点（core_spots），0 / 1
        + w_behavior · B(p)        # 同行人行为匹配
        + w_level · L(p)           # 景区等级：5A/4A 得 1，3A 及以下 0
```

**同行人行为匹配** `B(p)`：把同行人（情侣/亲子…）映射成一组加权体验词（`crowd_to_tags`），
再和 POI 的 `behaviors` 求匹配：

```
matched = [mapping[b] for b in p.behaviors if b in mapping]
B(p)    = (0.7 · max(matched) + 0.3 · mean(matched)) / max(mapping.values())
```

用「最大值 + 均值」是兼顾「命中一个高权重词」和「整体契合度」。

**距离惩罚**（反扎堆，避免一天里挑出 5 个挨在一起的点）：

| 离最近已选点 | 系数 |
|---|---|
| < 0.5 km | × 0.1 |
| < 1.5 km | × 0.6 |
| < 2.0 km | × 0.8 |
| 否则 | × 1.0 |
| （core_spot 惩罚减半，往 1.0 拉） | |

**加权随机抽取**：第 i 个点的被抽概率 = `base_i × penalty_i` 归一化，逐个抽 N 个，最后按地理最近邻排序。

**三套风格的权重**（差异化的来源）：

| 维度 | 综合 | 口碑 | 悠闲 |
|---|---|---|---|
| `w_rating` 评分 | 0.15 | **0.25** | 0.10 |
| `w_interest` 兴趣 | 0.10 | 0.05 | 0.10 |
| `w_random` 随机 | 0.15 | 0.10 | **0.25** |
| `w_core` 核心景点 | **0.30** | **0.30** | 0.25 |
| `w_behavior` 同行人 | **0.30** | 0.15 | **0.30** |
| `w_level` 景区等级 | 0.00 | **0.15** | 0.00 |
| `target_count` 每天点数 | 5 | 5 | **4** |

- **综合**：均衡，靠 core + behavior 撑主干。
- **口碑**：质量优先，rating + 等级权重最高，随机最低；且 **5A 必选**（当天有 5A 就锁定，不参与随机）。
- **悠闲**：节奏慢，随机最高、每天少一个点。

seed 按 `(风格, 第几天)` 偏移——否则不同风格 / 不同天共用同一条随机流，
「悠闲」会退化成「综合」砍掉一个点。

> **一个隐含前提**：`pick()` 里有一条捷径——「当天候选池 ≤ 目标数 → 全选」。
> 所以**召回量必须足够大**（每天候选池明显大于 5），风格才分得开，地标也不会漏在召回之外。
> 因此召回数定为 `max(40, 天数 × 20)`，封顶 120。

## 生成层：风格前置，每天一次大模型

**用户在表单里先选风格，系统只生成那一种。**

生成流程：

```
召回 → 地理分天 → 按所选风格选点（点定死）
     → 每天一次独立大模型调用（并行），只写文案
     → 按 Day 顺序组装
```

**为什么要「点定死」**：大模型不参与选点，就不会编造景点、不会排出跨城行程。
它拿到的 prompt 只包含：

```
【用户需求】
城市：武汉
兴趣偏好：历史人文、自然风光
同行人：情侣
行程共 3 天，这是其中：Day1
住宿地：武昌区

【本日景点】（共 2 个，必须全部出现，不得增删）
1. 黄鹤楼（含 黄鹤楼公园/黄鹤楼故址） | 历史人文,自然风光 | 武汉地标，江南三大名楼之一
2. 晴川阁（含 晴川阁-禹稷行宫） | 历史人文,自然风光 | 临江古阁，可眺望长江

请写 Day1 这一天的行程文案。
```

**没喂给大模型**：坐标、评分、地址、营业时间、图片、候选池里的其它点、其它天的点、检索 query 原文。
——它只负责「把这一天的点写成人话」。

**系统 prompt 的硬约束**：

- 只能用【本日景点】里给出的地方，**不得增加、删除、替换**；
- 只能调整叙述顺序和时间安排；
- 以住宿地为中心安排，不要写「从 XX 站出发」。

**调用参数**：`qwen3.8-max`，走 OpenAI 兼容接口，`enable_thinking=false`（关深度思考，写文案不需要且更慢），
`temperature=0.7`，每天一次调用并行（`ThreadPoolExecutor`）。

**每天一次而非一次输出全程**：每天 prompt 很小、模型不容易跑偏；每天独立，前端天然能一天一个框；
能并行，N 天 ≈ 一次耗时。代价是模型看不到「昨天去了哪」，但行程展示不需要这个。

**校验（只记日志，不阻断）**：生成后检查文本里有没有「全库有、但当天清单没有」的景点、
以及清单里的点是否都被提到。**只写日志，不改文案**——大模型顺带提一句邻近景点
（如「登晴阁望长江、看龟山与黄鹤楼隔江相望」）是加分项，不算违规。

## 前端

Streamlit 单页：

- **表单**：城市 / 行程风格 / 兴趣（多选）/ 同行人 / 天数 / 出发地 / 住宿区
  - 城市放在表单外，换城市立刻联动刷新「出发地 / 住宿区」选项
- **地图**：folium + **高德瓦片**（中文标注，国内可加载）
  - 每天一个色块：凸包 → Chaikin 切角磨圆 → **膨胀到完全包住当天所有点**（有包裹感）
  - 色块上标 `Day1 / Day2`（放在色块西北角，不挡景点）
  - 景点按序号标数字；**不画连线**（大模型会按「早晚」重排顺序，连线反而误导）
- **每天一个卡片**：`DayN` 标题 + 文案 + 景点缩略图（点击跳原图）
- **「换一批」**：换随机种子重摇，契合「多样化 / 随机化」的产品定位

## 已知限制

- **只支持武汉**：重庆 / 南京配置就绪，但还没跑完整流水线。
- **郊区被搁置**：城郊分离后，郊区簇不进当前分天（只有「天数多到有空片」时才整体塞一片）。
  当前定位是**城区规划**。
- **检索相关性**：语义检索对「购物休闲」这类偏泛的兴趣召回偏弱，
  部分地标会排在候选池靠后的位置（这也是 Hit Rate 没有更高的原因）。
- **池小的一天无风格差异**：某些查询下某天候选本身就很少，三套风格会一样——
  这是「没得挑」，属正常现象。
