# 智能旅行规划系统

基于 RAG 的智能旅行规划系统。用户填写旅行偏好，系统检索景点知识库，调用大语言模型生成三套差异化行程方案，用户可自行选择。

## 项目演示

用户输入：城市、兴趣偏好、同行人、天数、出发地、住宿区域

系统输出：三套行程方案（综合 / 口碑 / 悠闲），每套按天分段，附带 AI 参考的候选景点清单

## 核心特性

- 配置驱动：城市、抓取词、过滤规则、字段规范全部写在 YAML 里，换城市只改配置，不改代码
- 五步流水线：crawl → clean → tag → build → eval，每一步独立、可单步重跑
- 两层过滤：硬过滤（地铁站、停车场等不可豁免）+ 软过滤（学校、政府机关等可豁免）
- LLM 自动打标签：用通义千问给每条 POI 生成兴趣标签、适合人群、一句话亮点
- 结构化检索：支持按城市、兴趣标签过滤，标签以数组存储，支持「或」逻辑多选
- 三套方案生成：综合 / 口碑 / 悠闲三种风格，一次调用生成，前端单选查看
- 评估体系：用 Hit Rate / MRR / Noise Rate 三个指标量化检索效果

## 技术栈

| 层 | 技术 |
|---|---|
| 数据源 | 高德地图 API |
| 大语言模型 | 通义千问（qwen-turbo 打标签 / qwen-plus 生成行程） |
| Embedding | DashScope text-embedding-v2 |
| 向量库 | Chroma |
| 框架 | LangChain |
| 前端 | Streamlit |
| 配置 | YAML |

## 快速开始

### 1. 安装依赖

```
pip install -r requirements.txt
```

### 2. 配置环境变量

在项目根目录建 `.env`：

```
AMAP_API_KEY=你的高德key
DASHSCOPE_API_KEY=你的dashscope key
```

### 3. 跑数据流水线（以武汉为例）

```
python -m src.crawl.amap_crawler --city wuhan
python -m src.clean.poi_cleaner --city wuhan
python -m src.tag.poi_tagger --city wuhan
python -m src.build.kb_builder --city wuhan
python -m src.eval.evaluator --city wuhan
```

### 4. 启动前端

```
streamlit run app.py
```

浏览器打开 http://localhost:8501

## 核心设计

### 配置驱动

所有城市配置放在 config/cities.yaml，POI 字段规范放在 config/schema.yaml。换城市、加字段只改配置，不改代码。

### 两层过滤

清洗阶段采用两层过滤：

- 硬过滤：地铁站、停车场、售票处等，命中即干掉，不可豁免
- 软过滤：学校、政府机关等，命中后看名字是否含豁免关键词（如「武汉大学」含「大学」则保留）

设计要点：硬过滤必须在豁免之前，软过滤才在豁免之后。否则「司门口黄鹤楼（地铁站）」会被核心词「黄鹤楼」抓到后豁免进来。

### 标签体系

三个标签字段，用途不同：

| 字段 | 来源 | 用途 |
|---|---|---|
| tags | LLM 生成 | 硬过滤（用户主动选的兴趣） |
| crowd | LLM 生成 | 软参考（写进 prompt，不过滤） |
| category | 规则映射 | 兜底分类 |

crowd 不做硬过滤的原因：标签是「倾向」不是「排他」。武汉大学没打「情侣」标签，不代表情侣不能去。硬过滤会误杀。

### 检索去重

检索结果按名字前 3 字分组，同一主景点最多返回 2 条，避免「黄鹤楼红墙」「黄鹤楼故址」霸榜挤掉主条目。

### 评估体系

用三个指标量化检索效果：

- Hit Rate@K：期望结果有多少被检索到
- MRR：第一个期望结果的排名倒数
- Noise Rate：不该出现的混入 top-K 的比例

## 已知问题与后续规划

### 已知问题

- 只支持武汉，重庆、南京尚未跑完整流水线
- 地标类查询（如「黄鹤楼附近」）检索不准，语义检索理解不了空间关系
- 组合类查询（如「历史 + 美食」）检索不准，单向量表达不了多意图
- 候选景点展示区会重复召回一次（每次展开重新调用）

### 后续规划

- [ ] 补重庆、南京，验证流程可复制
- [ ] 地理检索：用 location 字段做距离过滤/加权，解决地标类查询
- [ ] 多路召回：query 拆成子意图分别检索再合并，解决组合类查询
- [ ] 行程导出（PDF / 图片）
- [ ] 遗传算法多目标行程优化

## 踩过的坑

1. 评估集用精确匹配，指标虚低
   「户部巷小吃一条街」匹配不上「户部巷」。改成包含匹配后，指标从 0.188 涨到 0.438。

2. Chroma 的 where 顶层只能有一个操作符
   多条件必须用 $and / $or 显式包起来，不能平铺在同一个 dict 里。

3. 数组字段用 $contains，不是 $in
   $in 是给标量字段用的（值在列表里），$contains 才是给数组字段用的（数组包含某元素）。诊断时 $in 命中 0 条，$contains 命中 5 条。

4. prompt 里给了什么，LLM 就倾向于输出什么
   候选清单里带「评分」，LLM 每提一个景点就带评分。最后把评分从清单里弱化，问题解决。

5. embedding 用的文本和给 LLM 的文本，是两回事
   混在一起是常见错误。embedding text 越丰富越好，给 LLM 的描述越精简越好。
